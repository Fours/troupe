# Changelog

This project follows [Semantic Versioning](https://semver.org/). Under 0.x, a minor version can break the API. 1.0 comes after milestone 5 ([0032](https://github.com/Fours/troupe/blob/main/docs/decisions/0032-1-0-comes-after-rehearsal.md)). Each design choice behind these entries has a record in [docs/decisions](https://github.com/Fours/troupe/tree/main/docs/decisions).

## Unreleased

- `@kylewillett/troupe/rehearsal`, for any runtime: deterministic simulation testing of a whole cluster in one process. `scenario({ nodes, spares, clients, durationMs, setup, workload, faults, invariants })` describes one, and `scenario.run({ seed, plan })` runs it: every node on a clock of its own, on a simulated network and database, with the faults in `plan`, plain JSON, or drawn from the seed. A run gives its `history`, JSON, the same byte for byte from the same seed and plan, its `violations`, and the overlaps `expected` past a lease's margin. `invariants` has `oneLiveInstance`, `acknowledgedWritesKept`, `noStaleReads`, `atMostOnce`, `orderPerPair`, `recovers` and `failoverWithin`, and any `{ name, check }` is an invariant too ([0034](https://github.com/Fours/troupe/blob/main/docs/decisions/0034-a-run-is-a-seed-and-a-plan.md), [0035](https://github.com/Fours/troupe/blob/main/docs/decisions/0035-safety-under-any-network-ordering-under-the-contract.md)).
- `rehearse(scenario, { seeds: { from, count } })` runs a scenario on seed after seed, and shrinks each failing run to the smallest plan that still fails the same invariant: faults removed, the rest made shorter and later, and the run cut just past the violation. Its report has each failure with its shrunk plan and the line that replays it, how many seeds each invariant failed, and the seeds whose two runs differed when `determinismEvery` asks for a second run. `ignore` counts invariants without failing on them, `maxFailures` stops early, `maxShrinkRuns` (default 500) bounds shrinking, and `onSeed` sees each seed. A stall is a violation called `stall` ([0034](https://github.com/Fours/troupe/blob/main/docs/decisions/0034-a-run-is-a-seed-and-a-plan.md)).
- `Run.replay` is one line that replays a run: its seed, mode, plan, end and first violation. `scenario.run({ replay })` runs it, and `replay(scenario, line)` checks that it finds the same violation again, and says so if it doesn't, since that means something in the run isn't deterministic. `scenario.run({ seed, plan, untilMs })` ends a run early, and `Run.untilMs` says where it ended ([0034](https://github.com/Fours/troupe/blob/main/docs/decisions/0034-a-run-is-a-seed-and-a-plan.md)).
- `invariants.failoverWithin` checks that a killed node's entities answer again elsewhere within the bound, not only that they run, as the milestone spec has it. `recovers` and `failoverWithin` don't judge a window that a run cut short with `untilMs` ended before ([0040](https://github.com/Fours/troupe/blob/main/docs/decisions/0040-planted-bugs-are-found-by-what-they-break.md)).
- **Breaking:** only the larger side of a split downs the rest. A node that has had a member unreachable for `downAfterMs` downs the unreachable members only if it can reach more than half of the members up or leaving, itself included. Otherwise it downs itself and leaves the cluster, as a downed node always has, and comes back only by starting again as a new node through its seeds. At exactly half, the side with the first seed that's a member keeps the cluster, and a side of one never does unless it's the only seed. Run nodes under a process manager that restarts a node once it has left, as the cluster example's Docker Compose file and Rehearsal's scenarios do. Before, each side of a partition downed the other, and the two halves never merged ([0042](https://github.com/Fours/troupe/blob/main/docs/decisions/0042-keep-the-majority.md)).
- A cluster lets no new member in while one of its members is unreachable, and a joiner asks again until it can. A restarted node at an unreachable member's own address still gets in at once ([0042](https://github.com/Fours/troupe/blob/main/docs/decisions/0042-keep-the-majority.md)).
- Members greet the seeds they have no live member at, and two clusters that downed each other settle it when they next meet: the hello now says what the sender has down and how large its side is, and the smaller side downs itself and rejoins. The new fields are optional, so the wire protocol stays version 1 ([0042](https://github.com/Fours/troupe/blob/main/docs/decisions/0042-keep-the-majority.md)).
- A leaving node keeps heartbeating and checking who it can hear until it has left, so a long handoff no longer gets it downed halfway, and a node still joining that's told it was downed gives up and joins again as a new node ([0042](https://github.com/Fours/troupe/blob/main/docs/decisions/0042-keep-the-majority.md)).
- Remoting closes a connection with no hello after 5 s and dials again. Membership's frames dial an address even while an older incarnation there is down, and a message for another incarnation than the downed one waits for it instead of being dropped ([0042](https://github.com/Fours/troupe/blob/main/docs/decisions/0042-keep-the-majority.md), [0043](https://github.com/Fours/troupe/blob/main/docs/decisions/0043-the-hunt-and-fencing.md)).
- A lease the shard store renews for a node that doesn't hold it, after a release that failed, a lease lost while a renewal was on its way, or an acquire that timed out after it landed, is given back a TTL after the node let it go, instead of being renewed for good. An acquire waits for a release of the same lease to finish, and won't take a lease back under the token of a release that never answered ([0043](https://github.com/Fours/troupe/blob/main/docs/decisions/0043-the-hunt-and-fencing.md)).
- A leaving region finishes when its last shard stops, however it stopped, and hands on a shard granted after the leave began. A shard tries a failed remember write again while its entity runs. A region never routes a message past messages waiting for its shard, and a message bounced by a stale holder goes back ahead of them, so order per pair holds ([0043](https://github.com/Fours/troupe/blob/main/docs/decisions/0043-the-hunt-and-fencing.md)).
- Rehearsal: `oneLiveInstance` adds up the database clock's jumps within one TTL when it judges whether an overlap is past the margin, and `failoverWithin` counts a fault that ended just before a kill as near it ([0043](https://github.com/Fours/troupe/blob/main/docs/decisions/0043-the-hunt-and-fencing.md)).
- What 1.0 promises: exactly each entry point's exports, as `test/package.test.ts` lists them, 182 names on twelve entry points, and their documented behaviour. A minor version can add `SystemEvent` types, dead-letter reasons, history entry kinds, fault kinds and Backstage frame types, so a `switch` over any of them needs a `default`, and each one's TSDoc now says so. Backstage's `PROTOCOL`, the cluster's wire version, the table SQL and the supported Node lines change only in a major version. From 1.0, **Breaking** means a major version ([0039](https://github.com/Fours/troupe/blob/main/docs/decisions/0039-what-1-0-promises.md)).
- The API review before 1.0 removed and renamed nothing. Every export of `/rehearsal` and every field of its types now has TSDoc, which the TSDoc test checks, as it does every other entry point ([0039](https://github.com/Fours/troupe/blob/main/docs/decisions/0039-what-1-0-promises.md)).
- A replay line carries the version that recorded it. A seed's plan and history are promised only within one version, so when a line from another version doesn't reproduce, `replay` names both versions rather than blaming non-determinism. Lines without a version still run ([0039](https://github.com/Fours/troupe/blob/main/docs/decisions/0039-what-1-0-promises.md)).
- Backstage's UI skips a frame type it doesn't know, as it already did an event type, so an older UI keeps working against a newer server ([0039](https://github.com/Fours/troupe/blob/main/docs/decisions/0039-what-1-0-promises.md)).
- The README has a Rehearsal section: rehearsing your own entity type, writing an invariant, replaying a failure, and what Rehearsal doesn't simulate. A test runs and typechecks its code, and the smoke test runs it from npm on Node 22, 24 and 26.

## 0.4.0 (2026-11-28)

For Steadfast: Backstage's UI, for a page to embed, from a new entry point. Released from 0.3.2, so Rehearsal still isn't exported. Nothing that worked in 0.3.2 changes.

- `@kylewillett/troupe/backstage/ui`, for a page to embed Backstage: `mountBackstage(element, { client, selected, onSelect, explain })` draws the inspector in a new child of `element`, on any `BackstageClient`, and returns `{ update(changes), unmount() }`. The page owns the selection: picking an actor calls `onSelect(path)`, and it's selected once the page passes it back as `selected`. `explain` is the page's own words after each panel's, as text. `update({ client })` starts over on a new system. React is inside the entry point, so a page needs none and the package still has no dependencies. Neither the main entry nor `/backstage` loads it. Invalid options throw `TypeError` when they're passed in ([0045](https://github.com/Fours/troupe/blob/main/docs/decisions/0045-backstage-embeds-with-a-mount-function-and-react-inside.md)).
- `@kylewillett/troupe/backstage` exports the `BackstageClient` type, the `connect` and `request` that Backstage's UI draws from. `BackstageSource` extends it ([0045](https://github.com/Fours/troupe/blob/main/docs/decisions/0045-backstage-embeds-with-a-mount-function-and-react-inside.md)).

## 0.3.2 (2026-11-24)

For Steadfast: a failure can raise its backoff restart delay, for a 429's `retry-after`. Released from 0.3.1, so Rehearsal still isn't exported.

- `supervise.restartWithBackoff` takes `minDelayFor: (failure) => number | undefined`. It's called with each failure as it was thrown, and returns the fewest ms the restart must wait, such as a server's `retry-after`, or `undefined`. The restart waits `max(backoff, minimum)`, with jitter on top, so never sooner than the minimum. The minimum isn't capped by `maxMs`, and doesn't count as extra backoff steps. A `minDelayFor` that throws, or returns anything but a non-negative integer or `undefined`, is logged at `error` and the ordinary backoff applies. Without it, backoff is unchanged ([0041](https://github.com/Fours/troupe/blob/main/docs/decisions/0041-a-failure-can-raise-its-backoff-delay.md)).

## 0.3.1 (2026-11-24)

For Steadfast: a piped promise that the actor's own timer ends no longer holds up the testkit's `advance`. Released from 0.3.0, so Rehearsal still isn't exported.

- `ctx.pipeToSelf(promise, map, { signal })`: when `signal` aborts, the pipe delivers `{ ok: false, error: signal.reason }` at once and ignores whatever the promise does later. A pipe with a signal isn't busy work, so the testkit's `settle` and `advance` let time pass while it's pending, and Rehearsal's run loop doesn't count it as a stall. Abort it from one of the actor's timers or its `postStop`. `settle` still gives it one event-loop turn, so a promise that has already settled arrives first. `PipeOptions` and `PipeSignal`, a structural type every runtime's `AbortSignal` fits, are exported from the main entry. `pipeToSelf` without options is unchanged ([0038](https://github.com/Fours/troupe/blob/main/docs/decisions/0038-a-pipe-with-a-signal-ends-on-the-scheduler.md)).

## 0.3.0 (2026-11-24)

Part of milestone 5, Rehearsal, released early for Steadfast: timeouts on every store call, and the JSON check as public API. Rehearsal itself isn't exported yet, and goes out with 1.0.0. The timeouts can break code, and are marked **Breaking**.

- **Breaking:** journal, snapshot, offset and shard store calls that never answer now time out, after 10 s for persistence and `renewMs` for the shard store, instead of waiting forever. Code that relied on a call waiting forever, such as a backend that answers only after minutes, needs a longer `timeoutMs` ([0036](https://github.com/Fours/troupe/blob/main/docs/decisions/0036-timeouts-are-unknown-outcomes-settled-by-recovery.md)).
- `persistentActor` and `projection` take `timeoutMs`, a positive integer, default 10,000. A journal call or a recovery read that takes longer fails the actor with `PersistenceTimeoutError`, for its supervision to handle, and a persistent actor sends no reply for a write that timed out. The write may still have been made, and the restart recovers from the journal to find out. A snapshot load that times out is skipped, and recovery replays every event. A snapshot save that times out is logged ([0036](https://github.com/Fours/troupe/blob/main/docs/decisions/0036-timeouts-are-unknown-outcomes-settled-by-recovery.md)).
- `PersistenceTimeoutError` in `@kylewillett/troupe/persistence`, with `id`, the persistence id or projection name, `operation`, a `PersistenceOperation`, and `timeoutMs` ([0036](https://github.com/Fours/troupe/blob/main/docs/decisions/0036-timeouts-are-unknown-outcomes-settled-by-recovery.md)).
- `joinCluster`'s `leases` takes `storeTimeoutMs`, a positive integer, default `renewMs`: how long each shard store call may take before the node gives up on it. A renewal that times out counts as failed, and the holder still gives its shards up at its deadline. A handoff waits for the entity's own timeout, never for a journal that doesn't answer ([0036](https://github.com/Fours/troupe/blob/main/docs/decisions/0036-timeouts-are-unknown-outcomes-settled-by-recovery.md)).
- `@kylewillett/troupe` exports `JsonValue`, `isJsonValue(value)` and `jsonProblem(value)`: the check events, snapshot states and messages to entities must pass, for code that wants to check a value before it's written. `jsonProblem` names where a value stops being JSON, as a path such as `$.items[2] is a hole`, or returns `undefined` ([0037](https://github.com/Fours/troupe/blob/main/docs/decisions/0037-the-json-check-is-public.md)).

## 0.2.0 (2026-11-24)

Milestone 4: multi-node. Three new entry points, `/cluster`, `/cluster/postgres` and `/cluster/tcp`, for cluster sharding across Node processes with at most one live instance of each entity. Still no runtime dependencies, and `/cluster` and `/cluster/postgres` run on any runtime. The core changes that can break code are marked **Breaking**: the `deadLetter` reasons, the new `SystemEvent` types, and Backstage's protocol version.

- **Breaking:** `deadLetter`'s `reason` gains `unreachable`, `unserializable` and `invalid`, for messages that can't reach another node, can't be sent as JSON plus refs, or fail an entity type's schema. A `switch` over the reasons that has no `default` needs the new cases ([0025](https://github.com/Fours/troupe/blob/main/docs/decisions/0025-messages-on-the-wire-are-json-plus-refs.md)).
- `@kylewillett/troupe/cluster/tcp`: `tcpTransport({ port, host, advertise, secret })`, a transport for nodes in separate processes, on `node:net` with length-prefixed JSON frames. Peers prove a shared secret by challenge and response before anything else, and it never crosses the wire. It listens on `127.0.0.1` by default, and doesn't encrypt, so keep cluster traffic on a private network ([0027](https://github.com/Fours/troupe/blob/main/docs/decisions/0027-nodes-talk-tcp-with-a-shared-secret.md)).
- `@kylewillett/troupe/cluster`, for any runtime: `joinCluster(system, { name, transport, seeds })` joins a cluster through its seeds, and returns a `Cluster` with `self`, `members()`, `whenUp` and `leave()`. Membership is gossiped with no leader. Nodes heartbeat each other, a member unheard for `unreachableAfterMs` is unreachable, and one unreachable for `downAfterMs` more is downed, which ends watches on it. Only the first seed forms a cluster alone. It also exports `inMemoryNetwork({ scheduler, latencyMs })`, nodes in one process on one scheduler, and the `Transport` and `Connection` interfaces ([0028](https://github.com/Fours/troupe/blob/main/docs/decisions/0028-membership-is-gossiped-with-automatic-downing.md)).
- **Breaking:** `SystemEvent` gains `memberUp`, `memberLeaving`, `memberDown`, `memberRemoved` and `reachability`, published only by a system in a cluster. A `switch` over event types that has no `default` needs the new cases ([0028](https://github.com/Fours/troupe/blob/main/docs/decisions/0028-membership-is-gossiped-with-automatic-downing.md)).
- Shard leases: the `ShardStore` interface and `inMemoryShardStore({ clock })` in `@kylewillett/troupe/cluster`, and a new entry point, `@kylewillett/troupe/cluster/postgres`, for any runtime, with `postgresShardStore({ pool, schema })` on the same `pg`-compatible pool as the journal. Its tables can share the journal's schema, its `setup()` is safe alongside the journal's, and its SQL ships as `dist/cluster/postgres/schema.sql`. A lease's expiry is judged on the store's own clock, Postgres's `clock_timestamp()`, never a node's ([0029](https://github.com/Fours/troupe/blob/main/docs/decisions/0029-a-shard-is-owned-by-whoever-holds-its-lease.md)).
- Cluster sharding: `cluster.sharding.init({ type, entity, shardCount, supervision, host, schema, bufferSize })` registers an entity type, and its `ref(id)` gives an `ActorRef` to the entity with that id, wherever it lives. Entity refs travel in messages and outlive shard moves. Messages to entities are always encoded, even on one node, so one that isn't JSON plus refs is an `unserializable` dead letter wherever its entity is, and one that fails the type's Standard Schema is `invalid`. Shards go to the member with the highest rendezvous score, through a lease. `joinCluster` gains `shards`, the `ShardStore` every node shares, and `leases: { ttlMs, renewMs, marginMs }`, and `Cluster` gains `sharding`. `sharding.init` also takes `passivation: { idleMs }`, `remember`, `rebalanceMs` and `maxHandoffs`. Nodes rebalance: a shard whose desired owner is another node is handed off, a few at a time. A node that leaves, or whose system terminates, hands off every shard before it goes. A handoff stops the shard's entities once they've handled what they have, a persist included, then releases the lease, and messages that arrived meanwhile follow the shard ([0030](https://github.com/Fours/troupe/blob/main/docs/decisions/0030-shards-are-placed-by-rendezvous-hashing.md)).
- **Breaking:** `SystemEvent` gains `shardAcquired` and `shardReleased`, with the entity type, shard, node and lease token, and a release's reason ([0030](https://github.com/Fours/troupe/blob/main/docs/decisions/0030-shards-are-placed-by-rendezvous-hashing.md)).
- `ActorRef.path`'s TSDoc says what a ref to another node has: the full `troupe://<cluster>@<address>#<uid><path>` form, so two refs with the same path are the same actor. An entity ref's path is `/sharding/<type>/<id>` on every node ([0025](https://github.com/Fours/troupe/blob/main/docs/decisions/0025-messages-on-the-wire-are-json-plus-refs.md)).
- **Breaking:** Backstage's protocol is version 2, and `PROTOCOL` exports its number. `hello` gains `cluster`, a `ClusterInfo` with this node's address and uid, the members as it sees them (`MemberInfo`) and each entity type's shard owners (`EntityTypeInfo`), or `null` for a system with no cluster. A third frame, `{ type: 'cluster', cluster }`, comes whenever that view changes. A client that rejects frames it doesn't know needs the new one. The UI, served by `serveBackstage`, shows a Cluster panel on a cluster node, with the members and a grid of shard owners, and the sharding tree above `/user`. The UI still reads version 1 ([0021](https://github.com/Fours/troupe/blob/main/docs/decisions/0021-backstage-only-watches.md)).
- `ctx.watch` and a probe's `watch` accept refs to actors on other nodes, and signal `terminated` when the actor stops or its node goes. Watching a ref that isn't an actor still throws `TypeError` ([0026](https://github.com/Fours/troupe/blob/main/docs/decisions/0026-remoting-is-at-most-once-behind-a-transport.md)).

## 0.1.0 (2026-11-22)

The first published version. ESM only, for Node 22.18 or later, with no runtime dependencies. Everything but the SQLite backend and the Backstage server runs on any JavaScript runtime.

### Actors (`@kylewillett/troupe`)

- `actor({ initial, receive, onSignal })`: an actor is a plain-value state and a reducer, with one message type that its refs are checked against. It handles one message at a time, async `receive` included.
- `createActorSystem()`: a hierarchy under `/user`, with `spawn`, `stop`, death watch with `terminated` signals, and `terminate()`, which stops children before their parents.
- `ref.tell` never throws: a message that can't be delivered, to a stopped actor or a full bounded mailbox, becomes a `deadLetter` event. `ref.ask` replies through a temporary ref under `/temp`, and rejects with `AskTimeoutError` after `timeoutMs`.
- Supervision, chosen by the parent at spawn: `supervise.stop()`, `resume()`, `restart({ maxRestarts, withinMs })` and `restartWithBackoff({ minMs, maxMs, randomFactor, resetAfterMs })`. A restart is a new incarnation, with `preRestart` first.
- Keyed single and periodic timers that belong to one incarnation, and `pipeToSelf` for promises.
- A shared dispatcher that gives each actor a turn of `throughput` messages and yields to the host every `yieldAfter`.
- The event stream: `failed`, `restarted`, `deadLetter`, and, for persistent actors, `persisted` and `recovered`. `delivered` and `processed` events, with mailbox depth and a best-effort sender, go only to listeners that pass `{ messages: true }`.
- Time, scheduling and chance are injected: `scheduler` and `random` options, and `realScheduler()`, whose `now()` is whole milliseconds.

### The testkit (`/testkit`)

- `createTestKit({ seed })`: a system on virtual time (`ManualScheduler`) and seeded chance (`seededRandom`), with `settle()`, `advance(ms)`, and every event and log line recorded.
- `kit.probe()`: a `TestProbe` whose ref records what it's sent, with `expectMessage`, `expectNoMessage`, `watch` and `expectTerminated`.

### Persistence (`/persistence`, `/persistence/sqlite`, `/persistence/postgres`)

- `persistentActor`: commands return effects (`persist`, `reply` and `none`, with `thenReply`, `thenRun` and `thenStop` chained after a persist), and the mailbox waits while a write is in flight. On start and restart it recovers from its latest snapshot and the events after it, then gets `recoveryCompleted`.
- Snapshots (`snapshots: { every, version }`), tags on events, schemas through Standard Schema, and versioned events with upcasters. Events and state are checked as JSON when they're written.
- A sequence check on every append, so a second writer to the same stream fails with `JournalConflictError` instead of forking it.
- `projection`: reads events by tag and keeps its offset, at least once.
- Three backends that pass one contract suite: `inMemoryPersistence()`, `sqlitePersistence()` on Node's `node:sqlite`, and `postgresPersistence()` on a `pg`-compatible pool it never imports. Each ships its table SQL in `dist/`.

### Backstage (`/backstage`, `/backstage/server`)

- `backstage(system)`: an in-process source of the inspector protocol, which is JSON frames with refs as paths: a `hello` with the actor tree and recent history, then events, plus requests for an actor's state, a persistent actor's timeline, and its state at any sequence number. `encode()` is the wire encoding for messages and state. Backstage only watches.
- `serveBackstage(system)`: serves the Backstage UI, which ships built in the package, on `127.0.0.1:7070`, and streams the system to it with server-sent events. It refuses requests whose `Host` header doesn't name the address it serves.
